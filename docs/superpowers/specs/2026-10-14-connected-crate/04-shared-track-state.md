# 04 — Shared favourites and deliberate metadata edits

Status: draft for review. Governing requirements: [Connected Crate](README.md). Requires verified track identity and the v2 extension capability on both clients.

## User outcome and enablement

Favourite a shared track on either client and see that preference on the other. Correct its display tags once and see the same deliberate values in both clients' library, details, player, export and supported smart rules. Device files and audio-engine properties are unaffected.

Add two options within existing **Crate connection** settings: **Share favourites** and **Share tag edits**. Enabling identifies the matched shared collection and requires the other client's supported capability. Do not enroll local-only music or other providers silently.

At first enablement, existing verified favourites seed the shared set as a union of positive selections. A missing local favourite is not an unfavourite event. Each client durably declares its complete bootstrap snapshot against the same acknowledged base catalogue generation defined below, identifying the exact enrolled IDs covered and its positive selections. The initial base-only generation does not include favourite decisions; completing it does not depend on finishing bootstrap. Bootstrap results enter a subsequent favourite-feature generation bound to that base. Until both snapshots arrive, show Preparing favourites and retain unknown shared states. Once both are complete, seed false only for verified catalogue entries with no positive selection on either client and no newer explicit revision; absence during discovery is never a removal. Live edits captured during bootstrap are preserved and rechecked transactionally rather than overwritten by seeding. Persist bootstrap completion per library and enrolled file ID. Later enrollment uses a new two-client bootstrap covering only newly enrolled IDs; it never reseeds existing decisions. A client must finish checking its local favourite mappings for the covered IDs before declaring its snapshot complete; an unresolved mapping is pending, not a negative selection. Thereafter explicit unfavourite writes a false value with ancestry. Tag edits share **new deliberate edits from enablement onward**; do not treat all imported fields or a row-level historical edit timestamp as per-field user intent. Existing corrections can be published through explicit **Use these tags on both devices…**, listing selected fields before committing.

Add **Edit tags…** to the current Mac track menu/details action area. Open a compact native form over the existing view with Save/Cancel; keep its read-only technical details. Reuse the phone's existing editor. The current Mac detail screen is primarily a display surface, so an editor and partial transaction-safe write path are required rather than assuming it already exists.

## Turning sharing off and on again

Each switch is a persisted **per-device, per-library** choice for its feature. Turning it off pauses that device's participation; it does not disable the other device, retract published records, delete shared values or restart bootstrap. Manual crates, audio publication and the other feature continue independently. Explain this in the settings copy.

| State/action | Required behavior |
| --- | --- |
| Turn off | Atomically close that feature's outgoing admission and incoming projection gate. Retain exact queued bytes, local intents, last shared baseline and bootstrap progress. Already admitted network writes may finish; reconcile their results without creating another revision. Show that already sent changes remain shared. |
| Edit while off | Save locally and retain per-field local-only divergence against the last shared baseline. Do not create shared revisions or silently include these edits in a later bootstrap. Existing visible values remain usable. |
| Receive while off | Discovery may durably retain remote records and advance its cursor only after storage, but must not apply them to local visible values. Do not acknowledge new shared-state generations for the disabled feature. |
| Turn on again | Enter **Review sharing changes** before resuming capture or delivery. Fetch remote heads (resolving any shared-head conflicts explicitly) and show retained outgoing work, local-only edits and incoming differences. Offer **Use shared values** or **Share my local changes** for affected fields; Cancel leaves sharing off and all work retained. |
| Complete reconciliation | Preserve already materialized immutable revisions and their bytes/ancestry. For unpublished intent, explicitly supersede it with the user's selected result; for materialized revisions, retain them and append a resolution covering them and current remote heads. **Use shared values** discards local-only divergence only after explicit confirmation; **Share my local changes** publishes only the listed, confirmed fields. Recheck heads/local generations and commit selection, projection, intent and enabled state atomically; stale review refreshes without losing drafts. Resume ordinary delivery afterward. |

Re-enable never repeats positive-union bootstrap for completed IDs. Pending first-time/new-ID bootstrap resumes with its original captured selections; subsequent local-only edits require the same explicit reconciliation. Feature-off local values never feed shared smart-rule evaluation. Dependent shared smart crates retain their last agreed result with **Sharing paused** and disable fresh playback/export until reconciliation and a new acknowledged generation complete. Local smart crates retain their ordinary behavior. Turning a switch off while an editor or reconciliation sheet is open invalidates its sharing admission; saving may proceed only as an explicit local edit.

## Shared fields and values

| Fields | Wire value and validation |
| --- | --- |
| title | NFC string, trimmed, 1–512 Unicode scalars, no C0/C1 controls. |
| artist, album, albumArtist, genre, label | NFC string, trimmed, 0–512 scalars; empty is an explicit cleared display value. |
| musicalKey | NFC string, trimmed, 0–128 scalars; preserve authored key notation, do not infer harmonic equivalence. |
| bpm | Null for unknown, otherwise finite 0–1000 number; 0 is distinct from unknown. |
| year | Null for unknown or integer 1–9999; adapt Mac string storage explicitly. |
| trackNumber, discNumber | Null for unknown or integer 0–9999. |
| favourite | Boolean; absent record means no shared decision, not false. |

Text fields use the same control exclusions as v1. Payload maximum is 64 KiB per field revision. Unlisted fields are rejected by this feature version, not silently stored. Duration, codec, bitrate, sample rate, channels, filesize, local URI, artwork URI, waveform/analysis, play counts and last-played are not editable shared values.

An edit record explicitly distinguishes **override** from **inherit**. Clearing a string sets an empty override; **Reset to file tags** removes the override through an explicit inherit revision. Null for numeric unknown is not an instruction to delete a track. Cancellation writes nothing.

## Identity, catalogue and conflict contract

Use `(verified libraryId, provider:dropbox, fileId)` as the wire identity. Path components use a deterministic SHA-256 encoding of the UTF-8 file ID, with the full identity verified inside the decoded body. Store aliases/projection separately. Do not treat native UUIDs or a preferred local encoding as a new shared track, or spread edits to a similarly named unverified recording.

The v2 track catalogue stores a versioned agreed base for each explicitly enrolled file ID: verified content hash, normalized source tags, read-only duration/lossless classification, and record ancestry. Initial base seeding explicitly uses verified Mac source tags, not localized Unknown Artist/Untitled display fallbacks; missing tags remain typed unknown values. User overrides remain separate and win. Only same-content records may converge automatically. Different-content or divergent base records require verification/review and retain the last agreed base. Missing base data remains unknown; never synthesize zero or delete a catalogue record because one device cannot see the file. This catalogue supports consistent metadata and later shared smart-rule evaluation.

## Catalogue enrollment and complete generations

Enrollment is an explicit collection-level choice: **Choose shared tracks…** in the existing connection settings lists recognizable track titles/artists and a count for confirmation; verified shared-file IDs stay internal. Sharing a regular crate or publishing audio does not silently enroll its files. Offer the same enrollment action for eligible newly shared/published tracks. Either client may request enrollment; Mac verifies the original shared-file content and source tags before supplying its base record. If Mac cannot verify it, show **Waiting for Mac verification** and retain the request. Enrollment is a monotonic union of confirmed IDs in this feature version; concurrent requests for the same ID are idempotent. Removing audio, losing access or omitting an ID from discovery cannot unenroll it. Catalogue removal needs a separately specified explicit action in a future version.

A generation is a finite, immutable snapshot, not a claim that no future Dropbox files exist. Its manifest identifies the verified library, the two participating persistent device IDs, generation UUID, parent generation, covered features (catalogue base, favourites and/or tag edits), full enrolled-ID set, exact base revision/content hash for each ID, and the complete head set for every field stream of its covered features. An explicit empty head set means **no shared decision at this snapshot**; an omitted entry is invalid. Feature coverage is explicit: a base-only generation can complete before either optional sharing feature is enabled. Favourites and tag-edit generations reference the same agreed base generation but may advance independently; an off feature cannot stall agreement for another feature. A combined evaluation snapshot pins compatible acknowledged feature generations to one base generation; it must never infer an uncovered feature's values from local data. The manifest also names both devices' durable publication checkpoints for its covered features. Each checkpoint identifies the exact captured revision set through a local monotonic capture sequence; locally pending/unmapped intent through that sequence prevents declaring it published. Missing base data may be represented as a typed unknown value inside a verified base record, never as a missing referenced record.

Mac coordinates generation proposals in persisted, serialized chains per feature coverage; phone-originated enrollment and field revisions join through the phone's publication checkpoint. Reinstallation/replacement of either participant requires explicit device re-pairing and a new participant-bound generation, preserving previous records and bootstrap decisions. Capability advertisement alone cannot replace a participant or acknowledge on its behalf. The normal reconnect of the same persistent device resumes pending work.

Use `.crate-sync/v2/catalogue/generations/<generationId>/` for the immutable manifest, bounded membership/head chunks and acknowledgements. The manifest references every chunk by immutable ID and SHA-256 of exact bytes; every document is at most 2 MiB. Chunks cover the declared set exactly once, with validated counts, identities and no duplicates. Publication persists all bytes first, uploads dependencies before the manifest and retries exact bytes. Arrival order is never evidence of completion. The implementation plan must lock the cross-language wire schema/fixtures before either writer is enabled.

A client acknowledges the exact manifest hash only after durably validating every chunk, referenced base/field revision and complete ancestry, verifying inclusion of both named publication checkpoints, and transactionally checking its own current capture frontier for the covered features. Unpublished local work in a covered feature, a known omitted revision, unresolved referenced base/field conflict or a disabled covered feature prevents acknowledgement and supplies a specific pending/review state. A newly captured edit before acknowledgement requires a successor proposal; accepted generations and their bytes are never amended. A generation becomes **agreed and complete** only after both participant acknowledgements are durably verified. Receiving a manifest, reaching the end of a list page or saving a Dropbox cursor cannot substitute for these checks.

Once agreed, the snapshot remains a valid historical snapshot even if either device later edits offline. Later enrollment, base changes and field revisions enter a successor generation; they do not change membership or values of the earlier one. A client with known newer work shows **Updating shared collection…** and does not label old results current. With no known newer work it may use its last agreed snapshot while showing offline/last-sync status; it cannot promise knowledge of unseen remote edits. Discovery stores obligations before cursor advancement, retries missing dependencies, and resumes after restart. A silent/offline/disabled peer leaves agreement pending with an actionable waiting state, without blocking local edits or v1 crate sync.

## Field revisions and projection

Each editable field is an independent immutable revision stream with library/track/field/version, revision ID, parent IDs, device ID and typed operation/value. Reuse v1's graph and exact-byte persistence requirements, bounded parent-resolution chains and strict identity validation. Different-field edits merge by independent streams. Sequential same-field edits follow ancestry, not wall-clock time. Identical concurrent field values may converge through a resolution revision covering both parents; different concurrent values require explicit review. Retain every conflicting value and pending intent.

While that feature is enabled, capture a field change, its local projection and outgoing intent atomically; while disabled, apply the local-only divergence rules above. Incoming projection updates only that field and suppresses echo capture. Do not copy whole `Track` rows between apps. Mac stores shared overrides separately from imported raw tags and updates effective query/cache projections transactionally. iPhone preserves `local_uri`, provider/media fields, aliases and ownership while applying through its mutation/media-claims boundaries. Rescan/canonical-promotion/importer paths retain deliberate overrides and cannot create false user changes.

A metadata editor carries per-field baseline tokens. Incoming changes to a draft's dirty field block its save with **Tags changed on your other device**; retain the draft and offer an explicit compare/resolve. Untouched fields can refresh. A conflict indicator opens a native field-by-field sheet with **Use Mac value** / **Use iPhone value**, retaining the current presentation until resolution. Favourite conflicts use the same explicit semantics and never discard either intent by timestamp.

Caches, album grouping, visible rows, player labels, exports and smart-match projections receive one postcommit invalidation. Do not recreate the player/source or reset scroll/selection merely because a tag changed. Remote favourite projection does not trigger Last.fm love/unlove; existing Last.fm integration remains a local deliberate-action option, preventing cross-device echoes.

Test missing/unmapped tracks before hydration and after later mapping. Then verify real two-device edits and native editors.

Additional acceptance gates:

| ID | Required observed result |
| --- | --- |
| S1 | Simultaneous enrollment, duplicate requests and later additions converge to the confirmed union. Unconfirmed files never enroll; missing files never unenroll. Bootstrap covers only new IDs and preserves existing false decisions. |
| S2 | Deliver manifest/acknowledgements before chunks, omit or corrupt a dependency, and interrupt/restart discovery: neither client claims completeness or seeds false from absence. Retry reaches the same agreed snapshot when all valid records arrive. |
| S3 | Capture an edit during proposal/acknowledgement: no acknowledged frontier omits known work. Concurrent edits resolve into a successor; offline edits after agreement do not mutate the old snapshot. Both clients produce identical values for the same manifest hash. |
| S4 | Disable each feature with pending intent, persisted bytes and an in-flight upload. Restart and receive remote changes: no new gated writes/projections occur, admitted writes reconcile, and all retained work survives. The other feature and v1 crates remain usable. With favourites off, a title-only smart rule receives a new tag generation; with tag sharing off, a favourite rule sorted by duration receives a new favourite generation. Neither waits for the disabled feature. |
| S5 | Edit/unfavourite while off; re-enable with remote conflicts. Cancel, Use shared values and Share my local changes each preserve or publish exactly the confirmed result. Stale reconciliation is rejected; immutable bytes remain unchanged; completed bootstrap never repeats or restores an old favourite. Test pending bootstrap and newly enrolled IDs as well. |

Listening-history synchronization and audio-tag writeback are excluded. Future history sharing needs immutable listening events; copying cumulative counts would double-count them.
